# B05 — Validator draft/published Builder v2.5

**Trạng thái:** module validator v2.5, fixtures và unit test đã có; Dũng đã review PR #97, đang xử lý nhận xét về semantic draft. **Chưa merge, chưa nối B09/B10, chưa nghiệm thu Gateway/E2E.** **Tiền đề:** R0 đã đạt theo cập nhật của người yêu cầu; B04 đã có catalog feature/preset trong API.  
**Owner:** An. **Reviewer:** Dũng (quyền, tích hợp B09/B10); Duy Anh đối chiếu issue/path với Web khi bàn giao F05.  
**Điểm nối:** B05 → B09 (draft/validate), B10 (revalidate khi publish). Không lấy việc B05 merge làm bằng chứng publish E2E đã đạt.

## Mục tiêu và phạm vi

Xây module validator riêng cho định nghĩa ứng dụng v2.5 theo hai schema [draft](../../reference/schema/digix-app-draft-v2.5.schema.json) và [published](../../reference/schema/digix-app-v2.5.schema.json), dùng danh mục **server B04** để kiểm tham chiếu/phụ thuộc/binding/quyền. Giữ nguyên đường đọc và validate Builder v1.0; app/draft v1 thiếu `startingPoint` vẫn đọc được. `startingPoint` chỉ là nguồn gốc tạo app, không quyết định feature hay quyền.

B05 không triển khai API/persistence/lock/checksum của B09, transaction/deploy/audit của B10, guard quyền runtime hay UI của F05. Những việc đó dùng kết quả B05 nhưng không được thay kiểm quyền tại API. Phạm vi và ca nghiệm thu theo [kế hoạch triển khai](../ke-hoach-trien-khai-chi-tiet-v2.5.md), [hợp đồng Builder/runtime](../../engineering/builder/hop-dong-ky-thuat-v2.5.md), [quyết định khởi công](../../engineering/architecture/quyet-dinh-khoi-cong-code-v2.5.md) và [ma trận nghiệm thu](../ke-hoach-nghiem-thu-v2.5.md).

## 1. Interface bàn giao để Dũng review trên PR

`apps/api/src/validator/app-v2.validator.ts` định nghĩa giao diện thuần, không truy DB:

```ts
AppV2Validator.validate(config: unknown, ctx: AppV2ValidationContext): AppV2ValidationResult
type AppV2ValidationContext =
  | {
      target: 'draft';
      catalog: CatalogFeaturesResponse;
      workflowTriggers: readonly { featureId: string; trigger: string }[];
      systemPermissions: readonly string[];
      componentVersions: Readonly<Partial<Record<CatalogComponent, readonly number[]>>>;
    }
  | {
      target: 'published';
      catalog: CatalogFeaturesResponse;
      scope: { tenantId: string; appId: string; version: number };
      pinnedCatalogVersion: string;
      inUseFeatureIds: readonly string[];
      workflowTriggers: readonly { featureId: string; trigger: string }[];
      systemPermissions: readonly string[];
      componentVersions: Readonly<Partial<Record<CatalogComponent, readonly number[]>>>;
    };
// AppV2ValidationResult = { valid: boolean; issues: readonly { code, path, message }[] }
```

`code` thuộc tập `APP_V2_ISSUE_CODES` xuất từ module; `path` là JSON Pointer (ví dụ `/pages/0/components/1/action`). Giao diện này **đã chọn để code/test**, vẫn cần Dũng review trước merge. Quy ước bàn giao:

- **Lưu nháp** dùng schema draft **và semantic cho dữ liệu đã nhập**: `features: []`, `roles: []`, `pages: []` được phép, nhưng feature phụ thuộc thiếu, binding/action/resource và permission sai phải trả issues. Nếu chưa khai báo role nào, không buộc component đã thêm phải có role sử dụng; tham chiếu `visibleToRoles` tới role không tồn tại vẫn là lỗi. **Kiểm khả năng publish** dùng schema published và cùng semantic, thêm kiểm scope, pin và feature đang dùng; nháp rỗng có issues cụ thể, không tạo runtime link. B09 quyết định chính sách lưu nháp khi có semantic issues, không được báo `valid: true` cho dữ liệu sai.
- Issue có `code` ổn định và `path` dạng JSON Pointer trỏ tới trường/page/component để Web dẫn tới chỗ sửa. B09/B10 quyết định HTTP `409`/`422`, snapshot checksum và lock; B05 không tự quyết định quyền gọi route.
- Cả draft lẫn published cần catalog, registry trigger, permission hệ thống và component version **do server cung cấp** để kiểm semantic. Published cần thêm scope đã xác minh, catalog version được pin và danh sách feature đang có hồ sơ/workflow. Thiếu context → `PUBLISH_CONTEXT_INCOMPLETE`; sai catalog pin/scope → issue cụ thể. `[]` là tập rỗng do server đã kiểm, không được dùng làm stub khi chưa biết trạng thái thật.
- `normalizeAppV2Ui` chỉ gọi sau schema validation, trả **bản sao** và không ghi lại snapshot published. Validation giữ nguyên input.

**Cách Dũng nối B09/B10:** B09 lưu `pinnedCatalogVersion` trong metadata app version (schema manifest v2.5 chưa có field này); PATCH gọi `target:'draft'` để kiểm cả hình dạng lẫn các tham chiếu đã nhập, `/validate` gọi `target:'published'` để trả lỗi khả năng publish. B10 lấy **cùng snapshot** draft + scope/metadata/catalog pin từ DB, lấy in-use feature và workflow registry từ service nguồn, lấy system permissions và component versions từ registry server; revalidate trước khi công bố version. Không nhận các field context này từ client; B05 không bảo đảm transaction/checksum. Nếu catalog lịch sử không thể truy lại theo version đã pin thì chặn publish, không dùng bản catalog mới để thay nghĩa config cũ.

## 2. Các lát triển khai

| Lát | Công việc | Bằng chứng tối thiểu |
| --- | --- | --- |
| **B05.1 — Schema** | Biên dịch riêng hai JSON Schema 2020-12 bằng AJV hiện có; chuyển lỗi `required`/`additionalProperties` và lỗi kiểu thành `{code,path,message}`. Không áp schema published để từ chối lưu nháp. | Test mảng rỗng draft; published thiếu feature/role/page hoặc page thiếu component; UUID, trường lạ, kiểu, layout, zone và version sai. |
| **B05.2 — Catalog/phụ thuộc** | Kiểm từng `featureId:version` có trong snapshot catalog, trạng thái được hỗ trợ, không trùng; dependency đầy đủ. Binding phải trỏ feature đã bật, resource/action có trong **chính feature đó**, component type được hỗ trợ. | Bỏ `crm.customers` khi còn `crm.opportunities`, bỏ `erp.materials` khi còn mua/kho; feature tắt, action/resource bịa, version không hỗ trợ bị báo đúng path. |
| **B05.3 — Trang/role/quyền** | Kiểm ID/path duy nhất, `menuOrder` và `order` không trùng trong phạm vi tương ứng, zone `side` không hợp lệ với layout `single`, mọi `visibleToRoles` tham chiếu role có thật. Permission role chỉ lấy từ danh mục/quyền hệ thống được công bố; binding của role phải có permission chính xác cho resource/action. `hidden` không cấp quyền. | `erp.inventory.stock.read` không suy ra `erp.inventory.receipts.read`; tương tự customers/contacts. Role không đủ quyền có issue tại page/component liên quan. |
| **B05.4 — Workflow/chuẩn hóa** | Kiểm ID/feature/trigger workflow theo registry đã chốt; kiểm component version được hỗ trợ. Khi thiếu trường UI tùy chọn, chuẩn hóa trên **bản sao**: `componentVersion=1`, `hidden=false`, `order` theo vị trí mảng; không sửa published snapshot bất biến tại chỗ. | Fixture cũ thiếu trường UI tùy chọn vẫn đọc/kiểm được, input không bị mutate; workflow/trigger không hợp lệ bị từ chối. |

B09 dispatch theo `schemaVersion` **lưu trong app version**, không suy từ body của lệnh validate; bàn giao fixtures, mã issue và ví dụ lỗi. | Regression đọc/validate draft v1 thiếu `startingPoint`; v2 không bị đưa qua validator v1; Dũng có test tích hợp với interface. |

**Ranh giới file:** ưu tiên module validator riêng do An sở hữu, dùng `CatalogService`/types của B04 qua interface; không để An và Dũng đồng thời sửa `builder-draft.service.ts` hoặc controller thuộc B09. Thay đổi vào module của Dũng cần review/ghép ở PR tích hợp của Dũng.

## 3. Ma trận kiểm thử

1. **Ca hợp lệ:** ERP bỏ kho nhưng giữ vật tư + mua; CRM thêm vật tư mà không tự bật mua/kho; blank sau khi chọn customers + opportunities; các fixture trong `docs/examples/*-app-v2.5.json`; bản v1 thiếu `startingPoint`.
2. **Schema:** draft rỗng lưu được nhưng publish bị chặn; published thiếu feature/role/page hoặc component tối thiểu; UUID/kiểu/version/zone sai, thuộc tính không khai báo bị từ chối.
3. **Semantic:** feature trùng/không tồn tại/khác version/không được hỗ trợ, thiếu phụ thuộc, component type không hỗ trợ, binding feature/resource/action sai, role/permission sai, path/order trùng, workflow tham chiếu sai.
4. **An toàn:** thay `startingPoint` không thay tập feature/quyền; `hidden`, preview role hoặc quyền `read` của resource khác không hợp thức hóa action; không cho cấu hình JS/SQL/URL tùy ý đi qua.
5. **Tích hợp B09/B10:** PATCH nháp rỗng thành công; validate báo issue có path; publish nháp rỗng/lỗi trả `422`, không tạo runtime link; publish kiểm lại snapshot/checksum dù client đã preview/validate trước đó. Test âm quyền route, `409` khi draft đổi và transaction publish do owner B09/B10 thực hiện.

Chạy unit test validator, regression Builder v1, build/typecheck API; sau khi B09/B10 nối, chạy test tích hợp qua Gateway với token thật. Map kết quả sang `TC-MOD-03`, `TC-START-01..04`, `TC-UI-02`, `TC-PUB-01` theo [kế hoạch nghiệm thu](../ke-hoach-nghiem-thu-v2.5.md). Unit test xanh hoặc PR merge **không thay** bằng chứng Gateway/Web của cổng R1/R3.

## 4. Quyết định/điểm chặn cần làm rõ sớm

1. **Pin catalog — quyết định đề xuất:** giữ pin ở metadata app version do B09 quản lý; B05 yêu cầu `pinnedCatalogVersion` và chỉ chấp nhận snapshot catalog trùng version. Dũng review nơi lưu/cách truy catalog lịch sử trước khi merge; không tự chuyển app cũ sang catalog mới.
2. **Component thiếu `action` — quyết định đề xuất:** `table/detail/metric` mặc định `read` trên đúng resource và không được bind action ghi; `form/action` buộc khai báo `action` có trong catalog. Mọi binding cần role tương ứng có đúng permission; nếu không có `visibleToRoles`, phải có ít nhất một role được quyền, API vẫn kiểm quyền tại thời điểm gọi.
3. **Workflow/feature đang chạy — quyết định đề xuất:** B05 chỉ nhận `workflowTriggers` và `inUseFeatureIds` do B10 cung cấp. Một action catalog không tự là trigger; thiếu registry/context phải bị chặn. Dũng review nơi cung cấp dữ liệu và thời điểm kiểm lại trong transaction. Đây là **điểm tích hợp B10 còn mở**, không được ghi nhận publish đạt trước khi hoàn tất.

## 5. Bàn giao và điều kiện hoàn tất

**Thứ tự:** interface + test hợp đồng → schema/semantic + regression v1 → Dũng review quyền/tích hợp B09/B10 → test tích hợp/Gateway. PR B05 ghi rõ interface, issue codes, fixtures, lệnh/kết quả test và các blocker còn lại. B05 hoàn tất ở mức **code/test đã review và B09/B10 tích hợp được**; publish thật, preview và nghiệm thu E2E vẫn thuộc B10/R3.

### Ghi chú triển khai hiện tại

- `apps/api/src/validator/` xuất `AppV2Validator`, `normalizeAppV2Ui`, `APP_V2_ISSUE_CODES` và `ValidatorModule`. Cả `target: 'draft'` và `target: 'published'` đều kiểm semantic; draft chỉ miễn các ràng buộc **chưa hoàn thiện** (mảng rỗng, role chưa khai báo), không miễn dữ liệu sai. Published kiểm thêm schema published và context server bắt buộc.
- Schema runtime có test đối chiếu trực tiếp hai schema ở `docs/reference/schema/`; mọi thay đổi hợp đồng phải sửa đồng bộ. Builder v1 không bị chỉnh sửa; B09 cần dispatch theo phiên bản lưu trong DB, B10 revalidate snapshot trước publish.
- **Fixture–catalog:** ERP dùng `action:receive` cho nhập kho (thay `form:receive`, không có trong B04) ở cả `docs/examples/` và bản Web tương ứng. Không thay registry B04.
- **Đã xử lý nhận xét PR #97 về semantic draft:** draft rỗng/thiếu role được phép, nhưng feature/action/resource/permission đã nhập sai trả issues; test âm tương ứng được bổ sung. Chờ Dũng xác nhận lại trên PR.
- **Chưa merge và chưa tích hợp:** B04 hiện không công bố workflow trigger/permission hệ thống/component version trong response; B05 không hard-code giả vờ là catalog. B09/B10 phải nối registry server thật và cung cấp context bắt buộc; Dũng review quyết định về pin catalog metadata.
