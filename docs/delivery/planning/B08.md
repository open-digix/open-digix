# B08 — CRM API

**Issue:** #105 · **Owner:** An · **Reviewer:** Dũng · **Dependency:** B06c PR #104 / issue #103.

## Implemented

- `/v1/apps/:appId/{customers,opportunities}` and customer contacts: create,
  list, detail and opportunity `advance`. API permission is checked per resource
  and action; the latest published app definition must contain the feature at
  version 1. No client-supplied tenant, app version or actor is trusted.
- Customer/contact/opportunity rows are scoped to tenant and app in SQL.
  Opportunities are additionally scoped to creator/assignee for list/detail/
  advance. Assignees must have an active membership and an app role.
- Every write uses the B06a `idempotency_keys` table in the **same transaction**
  as the CRM write; same key/payload replays the committed response, changed
  payload conflicts. An uncommitted claim is rolled back with the write.
- `advance` compares stage and lock version in SQL, writes the next stage and
  one actor/version event atomically; `won` is terminal.
- Customers and opportunities can have distinct app version IDs within the same
  app, pending Dũng's schema decision in #103.

## Verification and limits

- Unit tests cover route permission mapping and input validation. Opt-in
  `crm.integration.spec.ts` runs against an isolated PostgreSQL DB
  (`CRM_TEST_DB=...`) and checks cross-app reads/FKs, replay, conflicting keys,
  concurrent advances, history and disabling a feature on a newer version.
- `crm.http.integration.spec.ts` exercises the actual HTTP controller, JWT and
  tenant guards, DB-backed app permission guard, role revocation with the same
  bearer token, missing tenant/app permissions, feature disablement, and
  pagination after a new API instance. Only the OIDC verifier is stubbed:
  these are **not** real signed JWTs or Gateway tests. Cursor tests force
  identical microsecond timestamps for customers, contacts and opportunities.
- The `FeatureModuleRegistry` advertises the two features, but its generic
  handler does **not** bypass actor/ACL context: it fails closed. B11 must
  provide a scoped runtime adapter before using this registry as an execution
  path; the HTTP routes here are the working B08 path.
- Gateway tests with real JWTs, a Builder-published application and restart
  verification remain for the R02/R03 integration gates. A seed version in the
  integration test is **not** proof of the publish/runtime path.
- Do not merge until B06c is merged and Dũng confirms #103. Do not mark B08
  accepted merely from unit/seed-DB tests.
